## 2. Recurring design moves (4-8 patterns the reference games use)

1. **One mechanic per level, layered cumulatively.** Almost every
   reference game (sb26, ka59, tu93, m0r0, wa30, sp80, cd82, …)
   makes L1 the bare mechanic, L2 introduces *one* new wrinkle
   (e.g. an enemy, a second axis, a new sprite kind), L3 composes.
   This is how §3.4 "difficulty by composition" actually shows up
   on disk. Cited examples: tu93 (L1 maze-step → L2 followers →
   L3 chasers); m0r0 (L1 mirror-orbs → L2 +hazards → L3 +movable
   post-stones); wa30 (L1 lock-and-drag → L2 drone competitor →
   L3 walls); ka59 (L1 push → L2 more pawns → L3 enemies).

2. **HUD as a single-line depleting bar.** A `RenderableUserDisplay`
   subclass holding `(self.max, self.current)`, `decrement()`, and
   `render_interface(frame)` that paints a coloured run on one
   row/column. Position varies: tu93 paints `frame[63, x]` (bottom),
   ar25 paints column 63 (right edge), sp80 row 0 (top), m0r0
   *both* row 0 and row 63. The bar is the only HUD many games
   ship.

3. **Per-level `level.get_data("StepCounter")` injection.** Levels
   declare their step budget in the `Level(..., data={...})` dict;
   `on_set_level` reads it and resets the HUD widget (tu93 line
   988-990 is the canonical shape). Decoupling the budget from the
   widget instance is what lets L1, L2, L3 all share the same
   widget object with different limits.

4. **Tag-based queries dominate sprite lookup.** `get_sprites_by_tag`
   is the universal way to ask "all walls", "all targets", "all
   enemies". Sprites carry semantic tags (`"wall"`, `"goal"`,
   `"sys_click"`) even though their *names* are opaque random
   tokens. `sys_click` in particular is the tag the engine uses to
   gate which sprites can be the target of an ACTION6 click —
   explicit, e.g. m0r0 line 720
   `level.get_sprite_at(imgcn, cmize, tag="sys_click")`.

5. **Multi-frame animations inside `step()` via a state cursor.**
   When a single action triggers a multi-frame animation (sb26's
   commit-marker walking left to right, m0r0's crash flash on
   spike collision), the game holds an integer cursor (e.g.
   `self.zgdmc` in m0r0, `self.bbiavyren` in sb26), increments it
   each `step()` call until the animation completes, and short-
   circuits `complete_action()` until done. The agent sees one
   action consume many frames.

6. **Two-sprite-swap idiom for state toggles.** Both variants
   (e.g. polarity-up vs polarity-down) live in the level; one is
   `InteractionMode.TANGIBLE`, the other `REMOVED`; toggling swaps
   the modes. Cleaner than `set_visible(False)` because collision
   is also gated. (Documented in `code/universal-scaffold.md`,
   used by m0r0's pair-merge logic and sb26's tile-swap.)

7. **`_get_valid_actions` only when actions are context-gated.**
   Most games inherit the default. sb26's example (line 1129) is
   the canonical pattern: when a tile is mid-drag,
   `_get_valid_actions` enumerates only the legal drop targets;
   when no drag is active, it lists all clickable shelves. Use
   this for "select-then-drop" mechanics; skip it otherwise.

8. **Levels share sprite definitions; per-level differences are
   placement and `data`, not new sprites.** All three of m0r0,
   sb26, tu93 declare a single `sprites = {...}` dict and reuse
   entries via `.clone().set_position(...).color_remap(None, c)`
   per level. The same sprite kind is recoloured on demand;
   only level structure changes.

## 3. Recurring anti-patterns (3-5 things to avoid in the generated game)

1. **Level-specific custom sprites that explode the bank.** m0r0
   ships `jggua-Level1` … `jggua-Level11` — eleven hand-drawn maze
   sprites for what is conceptually "the same maze in different
   shapes". This works only because m0r0 has many levels; for our
   3-level cap it is wasteful. Prefer ONE parameterised maze
   sprite (or a small handful) and reposition / re-tag.

2. **Behavioural state encoded as pixel-mutation inside the
   sprite's `pixels` array.** tu93 (and to an extent m0r0) writes
   directly to `sprite.pixels[0,1] = fltjxhzdlv` to mark a sprite
   as "active". This is fast but fragile: the visual change is
   indistinguishable from "the artist drew a different shape", so
   the player must guess. Use `color_remap`, `set_interaction`, or
   tag membership instead — those are first-class state.

3. **Single-mechanic scaling across levels.** ar25, cn04, dc22,
   ft09, lp85, sb26 (per its frequency table line: "1 mechanic;
   L2 expansion; L3 frame variety") all do this — one mechanic in
   L1, more pieces / wider grid / more frames in L2/L3. The
   technical report flags this as the canonical anti-pattern (§3.4
   "single mechanic that scaled in size"). Our generated game
   MUST introduce a *qualitatively different* second mechanic by
   L2, and require both together in L3.

4. **Rendering symbols that the player will read as text.** Even
   though no glyph in the reference 25 spells letters or digits,
   several get close: sb26's number-suffixed frame names
   (`pcrvmjfjzg3` literally has a digit in its name, though only
   internally). For us, sprite *names* are fine to be opaque — the
   *rendered* pixels must NOT form letters/digits/clipart.

5. **Hidden randomness in `step()`.** None of the 25 reference
   games use `random.random()` mid-step; everything is
   procedurally seeded only at level-build time (e.g. bp35, lf52)
   or fully deterministic. The generated game must follow suit —
   recordings must replay (§3.5).

## 4. Open questions for `pick_mechanic`

1. **Action palette: click-only, arrow-only, or mixed?** The 25
   are roughly split 6 click-only / 7 arrow-only / 12 mixed. A
   cleaner mechanic comes from picking ONE of {arrows-with-modal,
   clicks-with-modal} and not trying to use both — fewer dead
   actions, smaller surface for the agent to model.

2. **Single-screen vs scrolling viewport vs camera-rescale?** The
   25 mostly use a fixed grid that fits inside 64×64; only ft09
   (scrolling 32×32 canvas inside 16×16 view) and a few others
   rescale. Default to fixed-grid for our 3-level game; only use
   a sub-window if the mechanic genuinely requires it.

3. **Step counter only, or step counter + accumulating resource?**
   25/25 use step counter; ~17/25 also surface an accumulating
   "captured / placed / matched" count. For a 3-level game, step
   counter alone is enough unless the win condition is N-of-M
   tickoff (then a visible progress dot per match helps).

4. **What core-knowledge prior pair?** physics+objectness (e.g.
   gravity / sliding / stacking) is over-represented; geometry+
   topology (mirroring / reflection / inside-vs-outside) shows up
   in a few (ar25, cn04). Agentness (a chasing or patrolling
   entity) shows up in 6 of the 25 (g50t, ka59, m0r0, su15,
   tu93, wa30). Less-explored corners of the priors-cube are a
   good place to look — e.g. **physics + agentness + topology**
   (an enemy whose pathing depends on level connectedness, or a
   self-driven blob whose direction reverses at topology changes).
