# lp85 — button-permutation-puzzle

## Summary
The board displays a small grid of named cells plus several click-buttons.
Each button is named `button_<name>_<R or L>` — the name and direction encode
a hard-coded permutation of cells (Rubik-style: rotate one face right or
left). Clicking a button physically swaps every cell sprite into the cell
position assigned by that permutation. The player must reach a goal
configuration: every `bghvgbtwcb` sprite ends up over a `goal` cell, and
every `fdgmtkfrxl` sprite ends up over a `goal-o` cell. Step budget is per-
level via `StepCounter` data. This is the largest source file (>21k lines)
because each level inlines its own permutation tables.

## Action mapping

| Action | Semantic (game-specific) | Gate / when valid |
|---|---|---|
| ACTION6 | Click a button to apply its permutation to the cell grid | only on a sprite tagged `sys_click` whose `tags[0]` starts with `button` |

(`available_actions=[6]` — no movement keys.)

## Per-level mechanic progression

| Level | Mechanic introduced (or composed) | Specific challenge / constraint |
|---|---|---|
| 1 | Few buttons (e.g. 4); each rotates a small subset | tutorial: try each button to learn its effect |
| 2 | More buttons; each L/R direction is a separate button | inverse pairs are explicit |
| 3 | Goal includes both `goal` and `goal-o` constraints | two simultaneous predicates |
| 4 | Composite buttons: some buttons combine multiple sub-rotations in their permutation | no decomposition; learn the combined effect |
| 5 | Multi-piece sprite types (square + circle pieces) | piece type matters for goal matching |
| 6 | Larger grid, 8+ buttons | longer planning |
| 7 | Tight step budget | minimum-permutation search |
| 8 | Final composite — full button set, both piece types, both goal types | nothing new |

(8 levels in the `levels` list; per-level button permutations are stored in
`chmfaflqhy(level_name, button_name, is_R, world_model)`.)

## Win condition
`khartslnwa()`: for every `bghvgbtwcb` sprite, a `goal` sprite at its centre
exists; AND for every `fdgmtkfrxl` sprite, a `goal-o` sprite at its centre
exists. Both → `self.next_level()`.

## Lose condition
Step counter HUD `toxpunyqe` (`fonypcnqmf`). Tracked via
`toxpunyqe.xsfawdkqoi()`. When zero → `self.lose()`.

## Internal state
- permutation engine `uopmnplcnv` (`qfvvosdkqr(izutyjcpih)`) — opaque, holds
  per-level permutation tables
- `ucybisahh` — cached level name string
- `afhycvvjg` — list of clickable button sprites, deduped by (x,y)
- step counter HUD `toxpunyqe`
- 16×16 camera with 4× scale (cells are 4×4 px)

## Notable code patterns
- Permutation as a lookup function: `chmfaflqhy(level_name, button_id, R/L,
  world_model)` returns a list of `(source_pos, target_sprite)` pairs;
  applying the permutation is just `set_position` for each pair. Reusable for
  any "click swaps cells in a fixed pattern" mechanic.
- Tag-encoded button identity: button sprites have a single tag like
  `button_<id>_<R>` and the parser splits on `_`. Avoids per-button code.
- Pre-deduplication of clickable buttons: any duplicate (x,y) loses its
  `sys_click` tag, so button overlap doesn't generate phantom clicks.
- Win predicate is purely "every key sprite has a goal sprite at its centre"
  — purely positional; the complex stuff lives in the permutation tables.
