# re86 — flood-fill-multi-canvas

## Summary
The player controls a colour marker (`vfaeucgcyr`) that moves across the
canvas with WASD. On each move, the marker's centre cell deposits the
marker's colour into the underlying paint canvas, while the marker also
"floods" by extending its boundary by 3 cells per move (when it enters a
hollow region). ACTION5 cycles which marker is currently active when there
are multiple. The level is won when the live painted canvas equals the
target canvas (`vzuwsebntu`) ignoring background pixels — the paint colour
of every target cell matches the painted canvas.

## Action mapping

| Action | Semantic (game-specific) | Gate / when valid |
|---|---|---|
| ACTION1 | Move marker up; deposit / flood paint | always |
| ACTION2 | Move marker down | always |
| ACTION3 | Move marker left | always |
| ACTION4 | Move marker right | always |
| ACTION5 | Cycle active marker if more than one exists | always (cycles regardless) |

## Per-level mechanic progression

| Level | Mechanic introduced (or composed) | Specific challenge / constraint |
|---|---|---|
| 1 | Single marker, simple path, one solid target colour | tutorial: walk over every target cell |
| 2 | Marker grows a "shell" boundary of paint each move | floods extend beyond the cursor; plan accordingly |
| 3 | Marker can shrink: hitting a wall (`miqpqafylc`) collapses an axis by 3 | reduce marker via wall-bumps |
| 4 | Two markers (`nogegkgqgd` and `ldkpywfara` types) — switch with ACTION5 | route both to fill different parts |
| 5 | Marker has different fill rule depending on tag (`nogegkgqgd` = paint centre to -1; `ldkpywfara` = paint centre with marker's hue) | tag-driven behaviour |
| 6 | Larger markers; multiple walls; tight paint count | careful navigation |
| 7 | Multiple targets requiring different paint colours per region | ACTION5-cycle to switch markers |
| 8 | Composite final: 2 markers, walls, partial overlapping targets | full stack |

## Win condition
`cdjxpfqest()`: build the canvas pixel grid by stamping every
`vfaeucgcyr` (paint marker) sprite into a canvas-sized array; compare to
target sprite (`vzuwsebntu`) pixels — if no live cell mismatches the target
(except -1/4 pixels), `self.next_level()`.

## Lose condition
Step counter `gimylktpny` (`nkrjkaokaj`) drains; when zero → `self.lose()`.

## Internal state
- active marker `zrermyobpw`; deselected marker `gwwpnjmvvo`
- step counter HUD `gimylktpny`
- per-marker colour stored in marker's pixels (`hfoimipuna` extracts boundary
  colour)
- markers tagged `vfaeucgcyr`; targets tagged `vzuwsebntu`; walls tagged
  `miqpqafylc`

## Notable code patterns
- Marker-as-rectangle whose boundary is a single colour and centre is a
  unique "tip" colour. Movement extends the boundary in the direction of
  motion by 3 px and shrinks the opposite side by 3 px (`np.zeros((H+3, W-3))`
  swap then re-paint borders).
- Wall-collision differentiates two kinds of marker via tag — reusable as
  "polymorphic agents with shared input".
- Canvas comparison via numpy boolean mask: `(marker.pixels != -1) &
  (marker.pixels != 4) & (marker.pixels != target.pixels)` — concise correctness check.
- ACTION5 cycle pattern: just iterate active marker through a fixed list.
