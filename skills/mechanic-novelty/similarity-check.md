# Mechanic similarity check

Used by `pick_mechanic` (when proposing a family) and
`critique_spec` (when the spec is fleshed out). Compares a
candidate against:

1. Every row in `taxonomy-of-25-games.md`. For any near-miss,
   read the deeper evidence layer at
   `deep-analysis-3lvls/<id>/<id>-deep-analysis.md`
   (authoritative — full sprite roster, action handlers,
   internal state, win/lose predicates, frequency-table). The
   shorter `skills/mechanism-details/<id>.md` summary is a
   useful first-pass overview but the deep-analysis is the
   ground truth for distinguishing-rule judgements.
2. Every row in `prior-games/index.md`.

## Procedure

For each row in either source:

### 1. Family-level check

Compare the candidate's `mechanic_family` tag (or family name in
the spec's section 2) to the row's `mechanic_family`. If they
match exactly OR share the same first two words after
hyphen-splitting, escalate to the description-level check.

### 2. Description-level check

Read the row's `description` and the candidate's full mechanic
description. For taxonomy entries, ALSO read the deeper view at
`deep-analysis-3lvls/<id>/<id>-deep-analysis.md`
(`skills/mechanism-details/<id>.md` is the shorter first-pass
summary; consult it if useful but the deep-analysis governs
when the two disagree). For prior-games entries, also read the
corresponding `prior-games/<id>/mechanism-detail.md` for the
deeper view (this file is generated by every successful run,
per `skills/finalize/mechanism-detail-template.md`). Ask:

- Does the candidate's WIN CONDITION match the row's win
  condition (after stripping cosmetic differences)?
- Does the candidate's PRIMARY ACTION match (move? click? rotate?
  swap? select-and-place?)?
- Does the candidate's PRIMARY CONSTRAINT match (step budget?
  hazard avoidance? fragile state? topology change?)?

If all three answers are yes, FLAG the row as too similar.

### 3. Distinguishing rule (only if flagged)

For every flagged row, the candidate's spec section 9 ("Novelty
note") MUST articulate the concrete distinguishing rule. Vague
language ("it has different colours", "it's harder") is not
acceptable. Concrete language is acceptable: e.g. "vc33 matches
column heights to a target; this candidate matches column heights
to the SAME column on the OPPOSITE side, requiring symmetric
play".

If no concrete distinguishing rule can be stated, REJECT the
candidate and re-pick a different family.

## Decision matrix

| Family match | Description match | Distinguishing rule? | Verdict |
|---|---|---|---|
| no | n/a | n/a | NOVEL |
| yes | no | n/a | NOVEL (cosmetic family-name overlap) |
| yes | yes | concrete | NOVEL (cite the rule in spec §9) |
| yes | yes | none / vague | REJECT — pick another family |

`critique_spec` re-runs this check on the FULL spec, not just the
family name; sometimes a fleshed-out spec drifts toward an
existing mechanic by level 3-4.
